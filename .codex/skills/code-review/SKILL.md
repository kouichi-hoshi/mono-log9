# 目的

- 変更差分から不具合と回帰リスクを早期に検出する
- 仕様・設計・実装・テストの不整合を明確化する
- 修正優先度が判断できるレビュー結果を返す

# 入力として確認する情報

- 変更ファイルと差分（必須）
- 関連仕様書・設計書・作業計画（必要な範囲のみ）
- 既存テストと実行結果（ある場合）

# 出力ルール

- 指摘事項を最優先で提示する
- 重大度順（`P0` → `P1` → `P2` → `P3`）で並べる
- 各指摘に `ファイルパス` と `行番号` を付ける
- 各指摘に「何が問題か」「なぜ問題か」「最小修正案」を含める
- 指摘がない場合は「指摘なし」を明記し、残留リスクと未検証項目を記載する
- 要約は最後に短く付ける

# レビュー手順

## 1. スコープを固定する

- レビュー対象の変更点と非対象範囲を明確化する
- 関連ドキュメントの真実源を特定する（仕様・設計・運用ルール）

## 2. 事実ベースで差分を読む

- 変更前後の振る舞い差を把握する
- 正常系・異常系・境界値・並行操作の影響を確認する
- 依存先の API、型、データ契約の破壊有無を確認する

## 3. 重点観点で検査する

- 仕様適合: 要件と実装結果が一致しているか
- 回帰: 既存機能を壊していないか
- 例外処理: 失敗時に安全な振る舞いになるか
- データ整合性: 更新順序・トランザクション・競合が安全か
- セキュリティ: 認可漏れ、入力検証漏れ、秘匿情報露出がないか
- 性能: 不要な N+1、同期ブロック、過剰再計算がないか
- 保守性: 命名、責務分離、重複、可読性が維持されているか
- テスト: 仕様変更に見合うテストがあるか

## 4. 重大度を判定する

- `P0`: 本番障害、データ破壊、重大なセキュリティ事故につながる
- `P1`: 高確率で不具合化する、または主要機能を阻害する
- `P2`: 品質低下や将来不具合の温床になる
- `P3`: 改善推奨（可読性、軽微な最適化、記述統一）

## 5. 修正可能な形で報告する

- 抽象論ではなく再現条件と根拠を示す
- 推測は推測と明記し、断定を避ける
- 修正案は小さく段階的な提案を優先する

# レビュー結果テンプレート

```markdown
## Findings

1. [P1] タイトル
   - 場所: `path/to/file.ts:123`
   - 問題: ...
   - 根拠: ...
   - 修正案: ...

## Open Questions

1. ...

## Summary

- 指摘件数: P0=0, P1=1, P2=2, P3=0
- 全体評価: ...
```

# 禁止・注意事項

- 根拠のない断定をしない
- 秘匿情報（APIキー、トークン、`.env*` の中身）を出力しない
- 未実行のテストを「成功」と表現しない
- 破壊的操作やDB更新を勝手に実行しない
