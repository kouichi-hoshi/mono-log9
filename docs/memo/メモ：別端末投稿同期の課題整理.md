# 別端末投稿同期の課題整理メモ

作成日: 2026-03-08

## 課題の定義

- PCで投稿を編集して保存したあと、スマホ側で同じ投稿を開いても、スマホの画面には古い `TanStack Query` キャッシュが残る。
- そのため、スマホ側で明示的にリロードしない限り、PCでの編集結果が反映されない。
- mono-log の現状は「同一端末内で自分が行った更新」は即時反映できるが、「別端末で発生した更新」を受け取る仕組みがない。
- 課題は次の2点に分けられる。
- 1. 別端末で保存された投稿更新を、現在表示中の端末へ通知すること。
- 2. 通知を受けた端末で、該当投稿の `TanStack Query` キャッシュを正しく更新または再取得すること。

## 解決方法

- Neon を使っていても別端末同期は実現可能である。
- Firestore のような組み込みリアルタイム同期はないため、投稿更新通知の仕組みを追加する必要がある。
- 現実的な構成は次の流れである。
- 1. 投稿保存時にDBの `updatedAt` を更新する。
- 2. サーバー側で「投稿が更新された」イベントを発行する。
- 3. 各端末は `WebSocket` または `SSE` でそのイベントを購読する。
- 4. イベントを受信した端末は `TanStack Query` の該当キャッシュを `invalidateQueries` する。
- 5. 必要に応じて詳細画面や編集中画面だけ `setQueryData` で即時反映する。
- 6. 競合対策として `version` または `updatedAt` 比較を導入する。
- mono-log では、まずは `invalidateQueries` ベースの構成が安全である。
- 理由は、一覧・favorite・trash・paging をまたぐ整合性をすべて `setQueryData` で自前同期すると複雑化しやすいためである。

## 現状の実装の概要

- 一覧取得は `useInfiniteQuery` で管理している。
- `mono-log9-app/lib/posts/usePostsInfiniteQuery.ts`
- `staleTime=5分`、`refetchOnMount: false`、`refetchOnWindowFocus: false`、`refetchOnReconnect: false` である。
- このため、スマホ側は前面復帰しても自動再取得しない。
- 同一端末内の更新反映は既に整備されている。
- `mono-log9-app/components/authed/AuthedScreen.tsx`
- `setQueryData` を使って現在の一覧キャッシュを更新している。
- `getQueriesData` で全投稿一覧キャッシュを走査して更新している。
- 差分更新できない場合だけ `invalidateQueries` にフォールバックしている。
- `mono-log9-app/lib/posts/cacheMutations.ts`
- favorite・trash・restore・delete のキャッシュ更新規則を純関数として切り出している。
- 設計上も「`setQueryData` を優先し、整合不能な場合のみ `invalidateQueries`」という方針になっている。
- `docs/designs/投稿一覧取得-キャッシュ-ページング_設計.md`
- DB側は `updatedAt` を持っている。
- `mono-log9-app/prisma/schema.prisma`
- 一方で、更新競合検知に使える `version` 列はまだない。
- 現状を要約すると次の通りである。
- 1. 同一端末内更新はできている。
- 2. 別端末同期は未実装である。
- 3. フォーカス復帰時の自動再取得は無効である。
- 4. `version` ベースの競合検知は未実装である。

## どう修正するか

- 段階的な導入が現実的である。

### 第1段階: 最小対応

- `visibilitychange` または `focus` 復帰時に投稿一覧を `invalidateQueries` する。
- これにより、リアルタイムではないが「リロード不要」で最新データへ寄せられる。
- 現状は同じ復帰イベントでセッション確認のみ行っているため、その導線に再取得を追加しやすい。

### 第2段階: 本命対応

- 投稿更新イベントを配信する仕組みを追加する。
- サーバーで投稿保存後にイベントを発行し、クライアントは `WebSocket` または `SSE` で購読する。
- 受信時に、該当 `postId` に関係する `posts` 系 query を `invalidateQueries` する。

### 第3段階: キャッシュ更新方針

- 別端末イベントの反映は、まず一覧側を `invalidateQueries` ベースにする。
- mono-log は infinite list と favorite/trash 分岐があるため、別端末イベントまで `setQueryData` で完全同期しようとすると複雑になる。
- まずは `["posts"]` 配下、または該当 `view` / `favoriteOnly` / `actorScope` の query key を無効化して再取得する方が安全である。

### 第4段階: 競合対策

- `version` 列を追加するか、最低でも `updatedAt` 比較を保存時に導入する。
- スマホが古い内容のまま保存した場合に、PCでの更新を上書きしないためである。
- シームレス編集を本格的に実現するなら、`version` 導入が望ましい。

### 第5段階: UX配慮

- 再取得中でも既存表示は維持し、画面全体をローディングで置き換えない。
- `isFetching` は静かに扱い、必要な箇所だけ更新中表示を出す。
- これにより、同期導入による体感劣化を抑えられる。

## 推奨する導入順

- 1. フォーカス復帰時の `invalidateQueries` を追加する。
- 2. 更新イベント配信を追加する。
- 3. `version` による競合検知を追加する。
- 4. 必要なら一部画面だけ `setQueryData` による即時同期を追加する。

## ユーザー操作シナリオ

### シナリオ1: 単一端末で通常保存する

- ユーザーがPCで投稿を開く。
- ユーザーが本文を編集して保存する。
- 保存時に、クライアントは編集中に見ていた `version` を送信する。
- サーバー側の最新 `version` と一致していれば保存成功とする。
- サーバーは `version` を1つ進め、更新イベントを配信する。
- 保存した端末では現在の一覧キャッシュを更新する。
- 他端末が接続していなければ、そのまま完了する。

### シナリオ2: PCで保存した直後にスマホへ反映される

- ユーザーがPCとスマホで同じ投稿を開いている。
- PCで投稿を保存する。
- サーバーは保存成功後に更新イベントを配信する。
- スマホがイベントを受信する。
- スマホは該当投稿に関係する `posts` query を `invalidateQueries` する。
- スマホ側で再取得が走り、リロードせずにPCの変更内容が反映される。
- このケースでは、スマホで未編集のままであれば競合は発生しない。

### シナリオ3: スマホが古い版のまま保存しようとして競合する

- ユーザーがPCとスマホで同じ投稿を開いている。
- PCで先に保存し、DB上の `version` が更新される。
- スマホは古い `version` のまま本文を編集して保存しようとする。
- サーバーは送信された `version` とDB上の最新 `version` を比較する。
- 一致しないため、保存は拒否し、競合エラーを返す。
- スマホ側では「他の端末で更新されました。最新版を確認してください」と表示する。
- スマホ側の入力内容は破棄しない。
- ユーザーは最新版を読み込むか、自分の入力を見直して再編集する。

### シナリオ4: 更新イベントを取りこぼした端末が復帰時に追いつく

- スマホがバックグラウンド中、または一時的な通信断で更新イベントを受け取れない。
- その間にPCで投稿が更新される。
- 後でスマホアプリが前面に戻る。
- `visibilitychange` または `focus` を契機に `invalidateQueries` が走る。
- スマホは最新データを再取得し、DB上の最新 `version` に追いつく。
- これにより、イベントを取りこぼしてもリロードなしで整合を回復できる。

### シナリオ5: 多数端末で同じ投稿を開いている

- ユーザーがPC、スマホ、タブレット、別PCで同じ投稿を開いている。
- どの端末も、それぞれが開いた時点の `version` を保持している。
- ある1台が先に保存すると、その保存だけが成功し、DBの `version` が進む。
- 他の端末は更新イベント受信または復帰時再取得によって最新状態へ追いつく。
- 追いつく前に古い `version` で保存しようとした端末は、端末数に関係なく同じ競合エラーになる。
- つまり、端末数ではなく「その端末が最新 `version` を見ているかどうか」だけで判定する。

### シナリオ6: お気に入りやごみ箱操作が別端末で行われる

- ある端末でお気に入り変更、ごみ箱移動、復元、削除が行われる。
- サーバーは更新イベントを配信する。
- 他端末は該当 query を `invalidateQueries` し、必要な一覧を再取得する。
- これにより、`favoriteOnly` や `trash` を含む複数一覧の整合性を保つ。
- 別端末イベントまで `setQueryData` で厳密同期するのではなく、再取得で整合を回復する設計とする。
