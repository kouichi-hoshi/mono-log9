# 目的

- 投稿編集（新規/更新）で扱う本文データの正を定義する
- フロントエンド、Server Actions、Repository 間の受け渡し契約を固定する
- 後続実装（項番17/18/28）で再設計が発生しないようにする

# スコープ

- 対象
  - 本文保存形式
  - create/update の入出力契約
  - `contentText` の位置づけ（役割）
  - バリデーションとエラー契約
  - バリデーション責務分担（フロント/サーバー）
- 前提
  - 実装着手前に、スタブ/既存データ本文は TipTap doc JSON へ変換済みであること
- 非対象
  - 一覧取得/キャッシュ/無限スクロール（`docs/specs/11`）
  - 認証/認可（Auth.js 本実装）
  - DB マイグレーション実行

# 基本方針

- 投稿本文の保存形式は TipTap（ProseMirror）doc JSON を正とする
- メモ/ノートで保存形式は分けない（どちらも JSON）
- Markdown 文字列および HTML 文字列は保存形式として採用しない
- URL パラメータは `view` を正とし、`mode` は内部概念として扱う（`docs/specs/09` 準拠）
- 表示形式は用途で分離する（ノート表示は `content` 由来HTML、検証/検索/フォールバックは `contentText`）
- サーバー側は Fail-Closed（許可した入力以外は保存しない）を原則とする
- サーバー内部では外部入力型と保存直前DTOを分離する（生入力を Repository へ直接渡さない）

# データ契約

## 投稿本文モデル

| フィールド | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `content` | TipTap doc JSON | 必須 | 本文の正データ。`type: "doc"` をルートに持つ |
| `contentText` | string | 必須 | `content` からサーバー側で導出するプレーンテキスト（検証/プレビュー用） |
| `title` | string \| undefined | 任意 | ノートタイトル |

補足:
- create/update のリクエスト項目は `mode` / `title` / `content` のみ
- `contentText` はサーバー内部で `content` から生成し、保存する

## `content` JSON 制約

- ルートは `{"type":"doc","content":[...]}` を必須とする
- 許可ノード
  - `paragraph`
  - `heading`（`attrs.level` は `2 | 3 | 4`）
  - `bulletList`
  - `orderedList`
  - `listItem`
  - `text`
  - `hardBreak`
- 許可マーク
  - `bold`
  - `link`

## 投稿作成/更新 I/F（契約）

### createPost

- 入力
  - `mode: "memo" | "note"`
  - `title?: string`
  - `content: TipTap doc JSON`
- 出力
  - 保存後の投稿レコード（`content` と `contentText` を含む）

### updatePost

- 入力
  - `postId: string`
  - `title?: string`
  - `content: TipTap doc JSON`
- 出力
  - 更新後の投稿レコード（`content` と `contentText` を含む）

## サーバー内部契約（検証済みDTO）

- Action 層は外部入力（create/update input）を parse/validate/normalize し、`Validated*Dto` を生成する
- Repository 層は `Validated*Dto` のみを受け付ける
- Repository は保存前の最小ガード（不変条件、状態遷移、整合性）を実施する
  - 例: `memo` で `title` を持たない、`contentText` 空禁止、`postId` の存在確認、`trash` 状態遷移の冪等性
- 同一の重い検証ロジックを Action/Repository に重複実装しない（共通関数を利用する）

# contentText の役割

- サーバー側バリデーション（空判定、文字数判定）
- 一覧表示時のプレーンテキストフォールバック
- 将来の全文検索/推薦用インデックス（導入時）

`contentText` の導出アルゴリズム、正規化、生成タイミングの詳細は設計書を正とする。

# バリデーション

- 最終判定はサーバー側で実施する（クライアント側は補助）
- 判定対象はサーバーが `content` から生成した `contentText`

## バリデーション責務分担

- フロントエンド（UX目的、任意）
  - 空入力の即時通知
  - 保存ボタン押下時の簡易チェック（例: 空判定）
  - サーバーからの `VALIDATION_ERROR` を表示する
- サーバー（必須、セキュリティ境界）
  - Action 層
    - リクエスト型検証（`mode`, `title`, `postId`, `content`）
    - `content` JSON 構造検証（許可ノード/マーク）
    - `contentText` 生成と文字数検証
    - 正規化（`title` trim, 空タイトルの `undefined` 化）
    - 検証済みDTO生成（Repository に渡す入力を固定）
  - Repository 層
    - 保存時の最小ガード（不変条件、存在確認、状態遷移、整合性）
    - 例外時のエラーコード正規化（`NOT_FOUND` / `VALIDATION_ERROR`）

補足:
- フロントとサーバーの判定が不一致の場合は、常にサーバー判定を正とする

## 検証対象一覧（サーバー必須）

| 対象 | 条件 |
| --- | --- |
| `mode` | `"memo" \| "note"` のみ許可 |
| `postId`（update） | 形式不正は `VALIDATION_ERROR` |
| `title` | string型のみ許可。trim後に100文字以内 |
| `content` ルート | `type="doc"` かつ `content` 配列を必須 |
| `content` ノード/マーク | 本仕様で許可した集合のみ |
| `contentText`（派生） | 空文字禁止、`memo<=280`, `note<=25000` |

| 条件 | 判定 |
| --- | --- |
| `contentText.trim().length === 0` | エラー（「内容を入力してください」） |
| `mode=memo` かつ `contentText.length > 280` | エラー（「内容は最大280文字までです」） |
| `mode=note` かつ `contentText.length > 25000` | エラー（「内容は最大25000文字までです」） |

## タイトル仕様

- `title` は任意（`mode=note` でのみ利用）
- 保存前に前後空白を trim する
- trim 後に空文字の場合は `undefined` として保存する
- 最大長は100文字
- 100文字超過時は `VALIDATION_ERROR`

# エラー契約

| 条件 | ステータス | エラーコード | メッセージ |
| --- | --- | --- | --- |
| `content` が不正 JSON 構造（doc ルート欠落、型不正） | 400 | `VALIDATION_ERROR` | 「入力内容に不備があります」 |
| `content` に不許可ノード/マークを含む | 400 | `VALIDATION_ERROR` | 「入力内容に不備があります」 |
| `mode`/`postId`/`title` の型不正 | 400 | `VALIDATION_ERROR` | 「入力内容に不備があります」 |
| 本文空 | 400 | `VALIDATION_ERROR` | 「内容を入力してください」 |
| 文字数超過（memo/note） | 400 | `VALIDATION_ERROR` | `docs/specs/06` の上限文言 |
| タイトル上限超過 | 400 | `VALIDATION_ERROR` | 「入力内容に不備があります」 |
| 更新対象が存在しない | 404 | `NOT_FOUND` | 「対象が見つかりません」 |

補足:
- Action 層または Repository 層のガードで入力不正が検出された場合、最終的な返却は `VALIDATION_ERROR` に統一する
- 対象不存在や状態不一致は `NOT_FOUND` を返す

# 表示・編集時の扱い

- 編集開始時は保存済み `content`（JSON）をエディタ初期値として使用する
- 一覧表示（投稿カード）の本文表示:
  - メモ: `contentText` を表示する
  - ノート: `content` から HTML へ変換し、サニタイズ後に描画する
  - ノート表示で HTML 変換/描画ができない場合は `contentText` をフォールバック表示する

# 受け入れ条件（DoD）

- 本文保存形式が TipTap doc JSON に統一されている
- create/update 契約で `content` と `contentText` の扱いが明文化されている
- 文字数判定がサーバー生成 `contentText` 基準で統一されている
- セキュリティ境界となる検証がサーバー側に実装されている
- `mode` と `view` の役割が混同されていない
- スタブ/既存データが JSON 化され、旧 HTML 互換なしで動作できる
