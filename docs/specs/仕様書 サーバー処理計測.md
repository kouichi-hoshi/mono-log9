# 目的

- 本番/stgでの体感遅延を、推測ではなく区間計測ログで切り分ける。
- `Action` 層と `Repository(DB)` 層のどちらが遅いかを `requestId` 相関で判定できるようにする。
- 調査時のみ詳細化し、平常時は env で出力制御できる運用とする。

# 対象範囲

- 対象アプリ: `mono-log9-app`
- 対象処理（現時点）
  - `post_action_perf`:
    - `listPostsAction`
    - `setFavoriteAction`
  - `db_post_repository_perf`:
    - `setFavorite`（`dbPostRepository`）
- 非対象（現時点）
  - `listPosts` のDB内訳（必要時に拡張）
  - 外部APM基盤への転送

# ログイベント仕様

## 1. `post_action_perf`

- 出力責務: `app/actions/postActions.ts`
- 目的: Action全体時間と `resolveRepositoryMs` / `repositoryMs` の比率把握
- 主なフィールド
  - `event`: 固定値 `post_action_perf`
  - `action`: `listPostsAction` or `setFavoriteAction`
  - `requestId`: リクエスト相関キー
  - `ok`: 成否
  - `totalMs`: Action全体
  - `resolveRepositoryMs`: auth + actor解決 + repository解決
  - `repositoryMs`: repository呼び出し時間
  - `errorCode`: 失敗時コード

## 2. `db_post_repository_perf`

- 出力責務: `lib/posts/repositories/dbPostRepository.ts`
- 目的: `setFavorite` のSQL区間を分解
- 主なフィールド
  - `event`: 固定値 `db_post_repository_perf`
  - `action`: 固定値 `setFavorite`
  - `requestId`: Actionと相関するID
  - `ok`: 成否
  - `totalMs`: repository処理全体
  - `clientResolveMs`: Prisma client取得時間
  - `probeEnabled`: `SELECT 1` プローブ実行有無
  - `probeMs`: プローブ往復時間（有効時）
  - `findFirstMs`: 参照SQL時間
  - `updateMs`: 更新SQL時間（更新時）
  - `sqlMs`: `probe/find/update` 合計
  - `nonSqlMs`: `totalMs - sqlMs`
  - `updateSkipped`: favorite値が不変で更新省略したか
  - `probeErrorCode`: プローブ失敗時コード
  - `errorCode`: 処理失敗時コード

# 相関ルール

- `post_action_perf.requestId` と `db_post_repository_perf.requestId` を一致させて判定する。
- 判定優先順位
  1. `repositoryMs` が支配的か
  2. `db_post_repository_perf.sqlMs` が支配的か
  3. `findFirstMs` と `updateMs` の偏り有無

# 環境変数（実行/停止制御）

- 既定値は「未設定で有効」。`false` を明示したときだけ停止。

| key | 既定 | 役割 |
| --- | --- | --- |
| `POST_ACTION_PERF_LOG_ENABLED` | 有効 | `post_action_perf` 出力制御 |
| `DB_POST_REPOSITORY_PERF_LOG_ENABLED` | 有効 | `db_post_repository_perf` 出力制御 |
| `POST_ACTION_SET_FAVORITE_DB_PROBE` | 無効 | `setFavorite` で `SELECT 1` プローブ計測を有効化 |

# 切り分け手順

1. `post_action_perf` で `totalMs` と `repositoryMs` を確認する。
2. 同一 `requestId` の `db_post_repository_perf` を取得する。
3. 次で判定する。
   - `sqlMs` が高い: DB往復/SQL側
   - `probeMs` も高い: region/ネットワーク要因が濃厚
   - `probeMs` は低く `findFirstMs`/`updateMs` が高い: SQL/ロック/実行計画要因が濃厚
4. 結果に応じて対処する。
   - region整合（Function Region と DB region）
   - SQL削減（往復回数削減、1クエリ化検討）
   - DB設定/実行計画確認

# 運用方針

- `dev/stg`: 基本有効（調査速度優先）
- `prod`: 平常時は必要最小限。調査期間のみ詳細ログを有効化
- 定期見直し:
  - 目標達成後は詳細ログを縮小し、恒久的には `action/ok/totalMs/requestId` 中心へ寄せる
