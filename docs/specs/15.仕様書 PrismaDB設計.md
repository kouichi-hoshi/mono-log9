# 目的

- 項番27で必要なDB要件（投稿/認可/一覧取得）を固定し、項番28/29の実装判断を揃える
- スタブ実装と実DB実装の挙動差分を最小化する
- DB制約で検知すべき不整合を明文化し、テスト観点を先に確定する

# スコープ

対象:

- 投稿機能（memo/note/trash/favorite）を支える最小DBモデル
- ユーザーと投稿の関連（認可境界）
- 投稿一覧（通常/ごみ箱）の並び順と取得条件
- 項番27時点で必要な制約・インデックス

非対象:

- DB運用手順（migration実行、CI/CD反映）
- 認証プロバイダ内部テーブル設計（Auth.js Adapter採用時の詳細）

# 前提

- DBは PostgreSQL を使用する（`docs/specs/02.仕様書 機能.md`）
- ORMは Prisma を使用する
- UUID採番は `gen_random_uuid()` を使用する（`pgcrypto` 拡張）
- 本文保存形式は `docs/specs/12.仕様書 投稿編集-本文形式.md` を正とする
  - `content`: TipTap doc JSON
  - `contentText`: サーバー導出のプレーンテキスト

# データモデル要件（項番27の最小）

## 1. User

- 投稿の所有者を識別するために `User` を持つ
- `User` は Googleログインの主体と1:1で対応する
- 最低限以下を持つ
  - `id`（主キー、UUID）
  - `googleSub`（Googleのsubject。ユニーク）
  - `email`（表示/運用補助。null許容）
  - `name`（表示名。null許容）
  - `image`（アイコンURL。null許容）
  - `createdAt` / `updatedAt`

### User同期仕様（Auth.js連携時）

- `googleSub` をキーとして `User` を突合する
- 既存ユーザーが存在しない場合は新規作成する
- 既存ユーザーが存在する場合は `email` / `name` / `image` を同期更新する
  - 取得できた値はDBへ反映する
  - 取得できない項目は既存値を維持する（意図しない `null` 上書きをしない）
- 同期後に得られた `User.id` を投稿の所有者キー（`Post.authorId`）として利用する
- 項番27の最小実装では、投稿系 Server Action 実行時に lazy upsert で同期してよい
- 将来 Auth.js のログイン成功イベントで同期してもよいが、upsert 契約は同一とする

### 認可コンテキスト受け渡し（項番27）

- 投稿系 Server Action は `auth()` でログイン状態を確認する
- 未ログイン時は `UNAUTHORIZED` を返す
- Action 層で `googleSub` から `actorUserId`（`User.id`）を解決し、Repository へ必須で渡す
- DB実装の Repository は `actorUserId` なしで投稿操作を実行してはならない

## 2. Post

- 投稿本体を表す
- 最低限以下を持つ
  - `id`（主キー、UUID。アプリの `PostRecord.id` に対応）
  - `authorId`（`User.id` 外部キー）
  - `mode`（`memo` / `note`）
  - `title`（任意。ノート向け）
  - `content`（JSONB相当）
  - `contentText`（本文抽出テキスト）
  - `favorite`（boolean, default `false`）
  - `status`（`active` / `trashed`）
  - `createdAt` / `updatedAt`
  - `trashedAt`（ごみ箱移動日時。通常投稿時は `null`）

## 2-A. API契約の補足（項番27時点）

- `Post.id` はDB上は UUID で保持し、APIの `postId`（文字列）は UUID を前提とする
- `postId` はスタブ実装/DB実装ともに UUID 形式のみを許容し、形式不正は `VALIDATION_ERROR` とする
- 日時:
  - DB保存値は `timestamp with time zone`（UTC基準）を用いる
  - `PostRecord.createdAt` / `PostRecord.trashedAt` の返却値は、既存UI契約に合わせ `YYYY-MM-DD HH:mm` 形式の文字列（JST）とする
  - cursor token の `t` は ISO 8601 UTC 文字列を使用する

# 状態遷移仕様

- 通常投稿: `status=active` かつ `trashedAt IS NULL`
- ごみ箱投稿: `status=trashed` かつ `trashedAt IS NOT NULL`
- `moveToTrash`
  - `active -> trashed`: `status=trashed`、`trashedAt=実行時刻`
  - `trashed -> trashed`: no-op（冪等）
- `restoreFromTrash`
  - `trashed -> active`: `status=active`、`trashedAt=NULL`
  - `active -> active`: no-op（冪等）

# 一覧取得要件

## 通常一覧（`view=memo|note`）

- 絞り込み条件
  - `authorId = ログインユーザー`
  - `status = active`
  - `mode = view`
  - `favoriteOnly=true` のときのみ `favorite = true`
- 並び順
  - `createdAt DESC, id DESC`

## ごみ箱一覧（`view=trash`）

- 絞り込み条件
  - `authorId = ログインユーザー`
  - `status = trashed`
- `favoriteOnly` は評価しない
- 並び順
  - `trashedAt DESC, id DESC`

## cursor 要件

- cursor token 契約（`v1` payload、デコード/検証、ページ継続条件、`INVALID_CURSOR` 判定）は `docs/specs/16.仕様書 Cursorページングトークン.md` を正とする
- `limit` は未指定時 `10`、許容範囲は `1..50` とする
- `limit` が許容範囲外の場合は `VALIDATION_ERROR` を返す

# 認可境界

- すべての投稿操作は `authorId = ログインユーザー` を必須条件に含める
- 他ユーザー投稿への操作は成功させない
- 対象不存在と他ユーザー投稿は区別せず `NOT_FOUND` として扱う（情報漏洩防止）
- 未ログイン状態では入力検証より先に `UNAUTHORIZED` を返す

# 完全削除ルール

- `deleteTrashPosts(postIds)` は all-or-nothing とする
  - 指定IDに1件でも「自分の `trashed` 投稿ではないID（不存在/他ユーザー/active状態）」が含まれる場合は `NOT_FOUND` を返し、削除は行わない
  - 全IDが自分の `trashed` 投稿である場合のみ削除を実行する
- `emptyTrash()` は `authorId = ログインユーザー` かつ `status = trashed` の全件を削除する

# 投稿APIエラー契約（項番29の正本）

- 本節は投稿系 Server Action（`listPosts` / `createPost` / `updatePost` / `setFavorite` / `moveToTrash` / `restoreFromTrash` / `deleteTrashPosts` / `emptyTrash`）のエラー契約を定義する
- UIは本契約に従ってエラーハンドリングを行う

| 条件 | ステータス | エラーコード | 補足 |
| --- | --- | --- | --- |
| 未ログイン（セッションなし、または `googleSub` から主体解決不可） | 401 | `UNAUTHORIZED` | 入力検証より優先して返す |
| 環境/設定ガード違反（例: スタブ禁止環境でスタブ導線を利用） | 403 | `FORBIDDEN` | 環境ガード時のみ返す |
| 入力不正（`limit` 範囲外、`postId` 形式不正、本文/タイトル不正など） | 400 | `VALIDATION_ERROR` |  |
| cursor 不正/参照不能 | 400 | `INVALID_CURSOR` | 詳細は `docs/specs/16.仕様書 Cursorページングトークン.md` を正とする |
| 対象不存在/他ユーザー対象/状態不一致 | 404 | `NOT_FOUND` | 情報漏洩防止のため同一コードで扱う |
| 想定外例外 | 500 | `INTERNAL_ERROR` |  |

優先順位:

1. 未ログイン時は `UNAUTHORIZED` を優先して返す
2. ログイン済み時は入力検証を行い、`VALIDATION_ERROR` / `INVALID_CURSOR` を返す
3. 対象解決に失敗した場合は `NOT_FOUND` を返す
4. `FORBIDDEN` は環境ガード違反時のみ返し、投稿CRUDの業務条件（所有権判定など）には使わない

# 制約要件

最低限のDB制約:

- `User.googleSub` はユニーク
- `Post.authorId` は外部キー
- `Post.favorite` は `NOT NULL`（default `false`）
- `Post.status` は列挙値制約（`active` / `trashed`）
- `Post.mode` は列挙値制約（`memo` / `note`）
- `User.id` / `Post.id` は UUID 型を採用し、ID生成は `gen_random_uuid()` を使用する
- `Post.title` は `varchar(100)`（null許容）
- `status` と `trashedAt` の整合は DB `CHECK` 制約で強制する
  - `active` なら `trashedAt IS NULL`
  - `trashed` なら `trashedAt IS NOT NULL`

補足:

- `content` JSON構造検証、`contentText` 文字数上限（memo<=280 / note<=25000）はサーバー側検証を主とする
- `contentText` はDBで最大長制約を設けず（text相当）、アプリケーション検証を正とする
- DB側で表現可能な範囲は制約化し、表現困難な検証はAction/Repositoryで担保する

# インデックス要件（最小）

位置づけ:

- 複合インデックスは本仕様の必須要件とする（実装最適化の任意項目ではない）
- 一覧取得（絞り込み + 並び順 + cursor継続）の性能/整合を満たすため、以下の組み合わせを固定する

- 通常一覧向け（favorite未絞り込み）
  - `(authorId, status, mode, createdAt, id)`
- 通常一覧向け（favorite絞り込み）
  - `(authorId, status, mode, favorite, createdAt, id)`
- ごみ箱一覧向け
  - `(authorId, status, trashedAt, id)`

# 受け入れ条件（項番27）

- Prismaで `User` / `Post` モデルが定義される
- 本仕様の制約・インデックス要件が `schema.prisma` および migration ファイルに反映される（migration実行は別タスク）
- 一覧取得の並び順要件（通常/ごみ箱）をDB実装で満たせる
- 認可境界（`authorId` 条件必須）がRepository設計に反映される

# テスト観点（項番27で先行確定）

- 未ログイン状態で投稿操作を行った場合に `UNAUTHORIZED` になる
- 制約違反時にDBエラーを正しく `VALIDATION_ERROR` へ変換できる
- 他ユーザー投稿への更新/削除/復元が `NOT_FOUND` になる
- 通常一覧・ごみ箱一覧の並び順が仕様どおりである
- `favoriteOnly` の有無で通常一覧の結果が正しく変化する
- `limit` が範囲外（非整数、0以下、51以上）の場合に `VALIDATION_ERROR` になる
- DB実装で UUID 以外の `postId` を受け付けない
- `status` と `trashedAt` の整合が破れない
- 同一 `googleSub` で再ログインした場合、同一 `User` を再利用し `email` / `name` / `image` が同期更新される
