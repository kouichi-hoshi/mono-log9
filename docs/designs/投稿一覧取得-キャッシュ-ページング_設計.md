# 目的

- `11.仕様書 投稿一覧取得-キャッシュ-ページング` の要件を、実装可能な形に落とし込む
- 画面切替時のちらつき防止と、一覧再利用時の即時復元を両立させる

# 全体方針

- クエリ状態（`view/favoriteMemo/favoriteNote`）は URL を正とする
- 一覧データ取得は TanStack Query（`useInfiniteQuery`）に集約する
- 投稿一覧表示は「現在の一覧条件と一致するキャッシュのみ」を描画する

# 一覧条件と queryKey

## 一覧条件

- `view`: `memo | note | trash`
- `favoriteOnly`: boolean
  - `view=trash` のときは必ず `false`

## queryKey 具体形

- 通常一覧:
  - `["posts", { view: "memo", favoriteOnly: false }]`
  - `["posts", { view: "memo", favoriteOnly: true }]`
  - `["posts", { view: "note", favoriteOnly: false }]`
  - `["posts", { view: "note", favoriteOnly: true }]`
- ごみ箱一覧:
  - `["posts", { view: "trash", favoriteOnly: false }]`

ルール:

- `cursor` は queryKey に含めない
- `cursor` は `pageParam` でのみ扱う

# useInfiniteQuery 設計

## 一覧取得I/F（実装契約）

- 呼び出し入口:
  - `app/actions/postActions.ts` の `listPostsAction`
- 入力型:
  - `ListPostsInput`
    - `view: "memo" | "note" | "trash"`
    - `favoriteOnly: boolean`
    - `limit?: number`（未指定時 `10`）
    - `cursor?: string`
- 出力型:
  - `ListPostsResult`
    - `items: PostRecord[]`
    - `hasNext: boolean`
    - `nextCursor: string | null`
- エラー:
  - 不正 `cursor` は `INVALID_CURSOR`
  - Action 戻り値は Result union（`ok: true|false`）に正規化して扱う

## queryFn

- `listPostsAction({ view, favoriteOnly, limit, cursor })` を呼ぶ
- 初回は `cursor` 未指定（`pageParam=undefined`）
- 追加取得は `cursor=pageParam`

## getNextPageParam

- `getNextPageParam(lastPage) = lastPage.nextCursor ?? undefined`
- `undefined` で追加取得終了（`hasNextPage=false`）

## キャッシュ/再検証オプション（仕様11対応）

- `initialPageParam: undefined`
- `staleTime: 5 * 60 * 1000`（5分）
- `gcTime: 30 * 60 * 1000`（30分）
- `refetchOnMount: false`
- `refetchOnWindowFocus: false`
- `refetchOnReconnect: false`

# 無限スクロール（IntersectionObserver）

- 一覧末尾に sentinel を配置
- 次をすべて満たすときのみ `fetchNextPage()`:
  - `hasNextPage === true`
  - `isFetchingNextPage === false`
  - `isRestoringScroll === false`
- `hasNextPage === false` のときは sentinel を非表示または監視停止

# ローディング/描画制御

- 初回読み込み:
  - 該当 key のページデータが空なら全体スケルトン表示
- 追加読み込み:
  - 既存一覧は保持
  - 末尾だけ追加スケルトン表示
- 背景再取得:
  - 既存一覧を保持し、スケルトンは表示しない
- ちらつき防止:
  - 現在の一覧条件と一致する key のデータのみ表示する
  - 画面切替直後に前画面データを描画しない

# エラー/再試行

- 初回取得失敗:
  - 明示エラー表示 + `refetch()` 導線
- 追加取得失敗:
  - 一覧維持 + トースト + `fetchNextPage()` 再試行導線
- `NOT_IMPLEMENTED`:
  - 空表示にせず、画面上に明示文言を表示

# スクロール位置復元

## 保存キー

- 一覧条件キー:
  - `scrollKey = "mono-log:scroll:v1:" + view + ":" + favoriteOnly(0/1)`
- 履歴エントリキー:
  - `entryId` を `history.state` に保持する
  - `entryScrollKey = scrollKey + ":" + entryId`
- `entryId` 未設定時は `history.replaceState` で採番したIDを付与する

## 保存タイミング

- URL変更直前
- 画面離脱（cleanup）
- 保存時は一覧条件キーと履歴エントリキーの両方へ同じ値を保存する
- popstate 遷移中は、未スクロール（`scrollY=0`）で既存の正値を上書きしない

## 復元タイミング

- 一覧描画後に `requestAnimationFrame` を待って `scrollTo`
- 復元中フラグ（`isRestoringScroll`）で無限スクロール監視を抑止
- 復元値の解決順序:
  - 1. 履歴エントリキー
  - 2. 一覧条件キー（フォールバック）
- 復元由来の `scroll` イベントはユーザー操作スクロールとして扱わない（保存判定から除外）

# 更新系操作時のキャッシュ更新

- 原則:
  - `setQueryData` による差分更新を優先
  - 差分で整合不能な場合のみ `invalidateQueries`
- 投稿操作別の基本:
  - お気に入り変更: 同一 `view` の関連 key（`favoriteOnly=true/false` の両方）を更新（favoriteOnly 中で解除なら除外）
  - お気に入り変更: 関連 key を差分更新できない場合は、関連 key を `invalidateQueries` する
  - ごみ箱投入: 通常 key から除外し、ごみ箱 key へ反映
  - 復元: ごみ箱 key から除外し、通常 key へ反映

# テスト観点（項番20）

- queryKey 分離（`memo/note/trash` + favorite）
- 初回/追加ロードのスケルトン出し分け
- 画面切替時の前画面データ非表示（ちらつき防止）
- 追加取得の多重発火抑止
- `nextCursor` による終端判定
- 初回失敗/追加失敗の再試行導線
- モード切替を複数回行った後の戻る/進む反復で、履歴位置ごとのスクロール復元が崩れないこと
- popstate 中に `scrollY=0` が観測されても、既存スクロール保存値が失われないこと
