# 目的

- `content`（TipTap doc JSON）から `contentText` を一貫して導出する実装手順を定義する
- create/update のサーバー処理順序を固定し、実装差異を防ぐ
- 項番17/18/28 で再利用できる共通ロジックを明確化する

# 実装方針

- `contentText` 生成はサーバー側の共通関数に集約する
- create/update は同一ロジックを使用する
- クライアントは `content` のみ送信し、`contentText` はサーバーで決定する
- セキュリティ境界はサーバーとし、検証はサーバー側を唯一の正とする

# モジュール構成（提案）

- `lib/posts/contentText.ts`
  - `extractContentText(content, mode): string`
- `lib/posts/contentSchema.ts`
  - `validateContentSchema(content): void`
- `app/actions/postActions.ts` または対応 Service
  - 受信→検証→導出→バリデーション→Repository 呼び出し

## バリデーションモジュール（提案）

- `lib/posts/validation/validatePostInput.ts`
  - `validateCreateInput(input): NormalizedCreateInput`
  - `validateUpdateInput(input): NormalizedUpdateInput`
- `lib/posts/validation/validateContentSchema.ts`
  - `assertValidContent(content): void`
- `lib/posts/contentText.ts`
  - `extractContentText(content, mode): string`

# `contentText` 導出アルゴリズム

## 入力

- `content`: TipTap doc JSON
- `mode`: `"memo" | "note"`

## 手順

1. `content` を深さ優先で走査する
2. `text` ノードの `text` 値を出力バッファへ追加する
3. `hardBreak` ノードは `\n` を追加する
4. ブロック終端で区切り改行を追加する
   - 対象: `paragraph`, `heading`, `listItem`
5. 生成後に正規化する
   - 改行コードを `\n` に統一
   - 連続改行を最大2つに圧縮
   - 各行の前後空白を trim
   - 全体を trim
6. `mode=memo` の追加正規化
   - 改行を半角スペース1つへ置換
   - 連続空白を1つに圧縮

## 出力保証

- 常に string を返す（`null` / `undefined` を返さない）
- `mode=memo` は改行なし1行文字列
- 同一入力で同一出力を返す（決定論）

# create/update の処理順序

## 共通フロー

1. 入力受信（`mode`, `title`, `content` など）
2. 基本型検証（`mode`, `postId`, `title`, `content`）
3. `content` JSON スキーマ検証（許可ノード/マーク）
4. `title` 正規化（trim、空なら `undefined`）
5. `contentText` 生成（`extractContentText`）
6. 派生値バリデーション
   - 空判定
   - memo 280 / note 25000
   - タイトル100
7. Repository 呼び出し
   - 保存データ: `content`, `contentText`, `title`, その他項目
8. 成功レスポンス返却

## エラー時

- 検証またはバリデーション失敗時は `400 VALIDATION_ERROR`
- メッセージは仕様書の契約文言を返す

## フロントエンド検証の扱い

- フロントエンドの空判定はUX改善のために残す
- フロントエンド検証を通過しても、サーバー検証は必ず再実行する
- サーバーが `VALIDATION_ERROR` を返した場合、フロントはその文言を優先表示する

# 一覧表示のデータ利用

- 投稿カード本文は `contentText` を使用
- リッチ表示が必要な画面のみ `content` から HTML を生成し、サニタイズして描画する
- 一覧本文表示の正は `contentText` とする

# テスト設計（最小）

## 単体テスト: `extractContentText`

- 見出し・段落・リスト・改行の組み合わせで期待文字列になる
- `hardBreak` が `\n` になる
- 連続改行/空白の圧縮が仕様どおり
- `mode=memo` で1行化される

## 単体テスト: バリデーション

- `mode` 不正
- `postId` 形式不正（update）
- `content` ルート不正（`doc` 欠落）
- `content` に不許可ノード/マーク
- 空本文
- memo 281文字
- note 25001文字
- title 101文字

## 結合テスト: create/update

- `content` 送信で `contentText` がサーバーで生成される
- 不正 `content` で `400 VALIDATION_ERROR`
- 正常保存時にレスポンスへ `content`/`contentText` が含まれる
- 不正 `mode` / `postId` / `title` で `400 VALIDATION_ERROR`
- 存在しない `postId` で `404 NOT_FOUND`

# 実装上の注意

- `contentText` をクライアント入力で受け付ける型を作らない
- `extractContentText` は UI 層から直接呼ばず、サーバー境界で利用する
- JSONスキーマ検証と導出ロジックは分離し、責務を混ぜない
- `postActions` で受けた入力をそのまま Repository へ渡さない（検証済みデータのみ渡す）
